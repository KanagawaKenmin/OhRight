# 视觉与手势优化交接 · 0.3.1 设计稿

日期：2026-10-26。对象：Sol 执行模型。此方案已按用户要求纳入 0.4.0 开发；实施与验证状态见[0.4 实施记录](体验改版实施_0.4.md)。本文 0.3.1 仅为原设计稿编号。

依据：用户实机截图、Telegram 侧滑截图，以及当前首页、卡片、详情和视觉样式源码。最新用户反馈优先于旧文档中“只对指定空白块加手势”“长按后换行展示操作”的约定。

配套：[可交互视觉示意](设计预览/视觉与手势.html)。这是布局、配色与交互方向示意，不是 SwiftUI 实机验收结果。

## 1. 必须修正的三个问题

1. 首页横滑应覆盖卡片以外的整个应用内容区域。现有 HomeBlankArea 只覆盖每项后面 16pt 与列表末尾留白；标题、说明、侧边距及其他空白未统一响应。
2. 当前 HomeActionCard 长按后切换 HStack/VStack，操作改变卡片布局；用户要的是卡片随手左移、右侧露出横排圆形操作，行高和其他卡片位置不变。
3. 详情页“转为计划 / 添加记录 / 做到了”是核心操作，却只有小胶囊；Markdown、预览、图片反而占据大块垂直空间。重排层级与尺寸，不修改业务含义。

## 2. 首页手势契约：先确定起点，再确定方向

“文本条”按整张事项卡片理解，包括标题、摘要、卡片内留白；不是只排除文字笔画。

| 手势起点 | 横向拖动 | 纵向拖动 / 点击 |
|---|---|---|
| 大标题、说明、分组标题、空状态、列表间隙、左右边距、底栏非按钮留白 | 左滑琐事→计划；右滑计划→琐事 | 纵向保留原滚动；普通点击可收起已展开卡片 |
| 卡片本体 | 左滑展开操作；右滑收起；不切模式 | 纵向滚动；未展开时点击进入详情 |
| 分段选择、更多、主按钮、通知提示按钮 | 保留控件自身交互，不让父级抢走 | 正常点击 |
| 文本编辑、选择文字、系统状态栏与系统边缘手势区 | 不接管 | 系统行为 |

- 起点命中后锁定归属；从留白滑过卡片仍切模式，从卡片滑到留白仍操作卡片。一笔拖动只能提交一种动作。
- 默认建议：移动约 10pt 后判方向，横向位移大于纵向 1.3 倍才认定横滑；纵向先成立则本次横滑识别失败。阈值是调试起点，须实机检查斜滑，不是硬编码的验收答案。
- 页面跟手平移；松手位移达页面宽度 20% 或预测终点达此值则切换，否则回弹。两页不循环，边界只轻微阻尼。
- 模式提交只在手势结束或分段点击时执行一次，拖动过程不得反复调用 model.selectMode 或写存储。
- 标题与底部入口位置稳定，两组列表横向过渡；每组独立保存滚动位置。当前隐藏页必须继续关闭命中和无障碍曝光。
- 系统大导航标题不天然属于内容视图的手势范围。把“哦对了”大标题放进首页内容头部，系统导航栏改 inline，保留更多入口；不要声称根视图加 gesture 就覆盖系统大标题。

## 3. 卡片侧滑：采用截图里的圆形动作语言

- 卡片前景随手平移，底层右侧固定横排三个动作：星标（已有星标则取消）、归档、删除。不要照搬 Telegram 的静音功能。
- 圆直径 48pt，图标 21pt，标签 12–13pt，圆之间留 12pt；每项实际可点击区域至少 44pt。操作区约 188–200pt；根据窄屏调整间距，不挤压原卡片文本。
- 星标用琥珀色，归档用蓝青色，删除用红色；标签在圆下。所有模式动作语义与色彩一致，删除不使用计划主题色。
- 展开进度驱动透明度与 0.85→1 的轻微缩放；卡片移动与圆形出现是同一次跟手动画。松手约 0.22 秒收敛，不能突然跳出，也不使用持续循环动效。
- 展开距离约为操作区宽度的 40% 时吸附打开，否则回弹；不实现全滑自动删除。
- 同时最多打开一张。打开另一张时关闭上一张；点击展开的卡片本体只收起；点击其他卡片正常进入详情并清空展开状态；空白点击、纵向滚动开始、切模式、离开首页都收起。
- 星标只切换星标；归档和删除复用现有 quickAction 与撤销机制。删除仍移入回收站。
- 长按不再生成另一套改变布局的小按钮。保留 VoiceOver 自定义动作；需要补充入口时使用系统上下文菜单，动作与侧滑共用。
- 辅助功能大字号下圆仍是圆，标签允许换行，操作容器可以增高；用无障碍动作补足操作，不能把标签缩到不可读。

## 4. 色彩与排版：青绿琐事、暖杏计划

现有背景：两模式共用近白底，琐事额外叠低透明度青紫模糊光团，计划几乎无背景特征。改为清晰、静态的模式底色。

| 令牌 | 琐事 | 计划 |
|---|---|---|
| 浅色背景，上→下 | #DDEFE8 → #F0F7F3 | #F7E4D4 → #FFF4E8 |
| 主色，用于文字与实心按钮 | #17685D | #984B25 |
| 轻色按钮 / 选中衬底 | #D3E8DF | #F3D9C5 |
| 深色背景 | #152922 | #302319 |
| 深色强调文字 | #8ED9BF | #F3BA8C |

- 卡片浅色白底，深色分别采用 #203A30 / #402F24；文字浅色 #202B27，深色 #F1F4F2。所有组合实施时检查普通文字对比度至少 4.5:1，不能只凭色值表认定已通过。
- 主按钮、分段选中项、状态标签跟随模式；保留“琐事/计划”文字，不只靠颜色表达状态。
- 取消常驻 TimelineView 漂浮背景；静态渐变已足够。只对用户操作触发的模式、侧滑和状态变化做短动画，减少动态装饰与等待空闲的不确定性。
- 默认字号：首页标题 30pt/粗体；卡片标题 19pt/半粗；摘要 15–16pt；详情标题 28pt/半粗，正文 17pt；区块标题 18pt；辅助说明 13pt。使用可随 Dynamic Type 缩放的语义字体，不锁死文字高度。
- 内容左右 20pt；卡片内边距 18pt、圆角 22pt；卡片间距合计 14pt。去掉现有外层 spacing 与额外空白块叠加造成的过大间隔。
- 两模式使用一致的圆角体系，以颜色和内容结构区分；不再让计划卡片和按钮突然变成小直角。

## 5. 详情页：三个核心动作全部整行宽

顺序固定：标题与状态 → 正文和附件 → 转为计划 → 补充记录编辑区 → 做到了 → 历史记录。

| 控件 | 布局与视觉 | 行为 |
|---|---|---|
| 转为计划 | 内容区等宽，最小高 52pt，轻色底、主色文字、日历图标 | 打开现有转换编辑页，取消不转换，保存保留 ID / 历史 |
| 添加记录 / 保存进展 | 编辑区等宽，最小高 54pt，主色实心、白字 | 仍按当前有效内容和图片导入状态控制提交 |
| 做到了 / 重新开始 | 内容区等宽，最小高 52pt，轻色底或描边 | 复用生命周期命令；计划暂停/恢复另起一行次级操作 |

- “全宽”指横向内边距以内的可交互区域，不是屏幕出血；frame 应施加在 Button 的 label 内，背景和命中区域跟随宽度，不能只把按钮外壳拉宽。
- “又想到一点”与输入框组成白色编辑卡：内边距 16pt，输入框默认至少 112pt 高，可随内容增高。
- 图片、Markdown、预览放在输入框下方的紧凑工具行，字号 14pt、实际点击高 44pt。Markdown 与预览保留独立状态，用带文字的选中按钮/菜单表达，设置 accessibilityValue，不再使用两条宽大系统开关行。
- 窄屏和大字号允许工具行换成两行。按钮标题不能截断；高度使用最小值。
- 预览位于工具行下、提交按钮上，保留草稿和格式语义；不为美化另写一套 Markdown 数据模型。
- 禁用提交按钮使用低饱和底和清晰的灰色文字，输入框占位说明写“补一句就好…”，避免白字落在浅灰底。
- 长正文正常滚动，不截断；三个核心动作各在自己所属区块，不把三枚主色按钮堆成相同优先级。
- 用户截图是 ItemDetailView，必须改此处。仅改 ItemEditorView 不会修复截图；独立编辑页与记录编辑页再复用同一工具行与按钮样式。

## 6. Sol 的工程实现顺序

1. 在 L3 共用层抽取颜色令牌、全宽操作按钮与记录工具行；先改详情及卡片静态样式，再接手势。
2. 首页设置唯一手势状态：idle / pageDragging / rowDragging(id)，以及唯一 openedItemID。只影响表现状态，保留已有 AppModel / L2 命令。
3. 使用统一首页坐标空间收集卡片、交互控件的可见命中边界。边界随滚动、布局、字号变化更新；不要通过“加更多透明空白块”补洞。
4. 做一个最小方向锁定原型验证首页横滑与 ScrollView 共存。若用 UIKit UIPanGestureRecognizer 桥接，shouldReceive 排除控件、shouldBegin 按方向与起点决定是否接管；同时识别与失败依赖只针对已知的竖向滚动关系配置。手势失效、页面卸载时清理识别器，不全局修改系统返回手势。
5. 不在根视图盲加 highPriorityGesture；onChanged 中 return 只是忽略回调，不能证明系统滚动识别器未被抢占。若选择纯 SwiftUI，同样必须通过下述起点与斜滑验收。
6. 卡片用固定尺寸 ZStack（底层动作 + 前景卡片 offset），替换按 selected 分支重排 HStack/VStack。记录操作过程中不触发详情导航；取消手势恢复稳定状态。
7. 页面横滑过渡复用两份列表及独立滚动位置；不要每帧销毁重建列表。导航路径、草稿、转换、撤销语义保持。
8. 更新模块文档、现有 UI 测试与源码清单后交付一个完整源码包。不要只给用户散落的补丁文件。

建议改动入口：`首页.swift`、`共用/首页事项操作卡片.swift`、`共用/视觉样式.swift`、`共用/事项卡片.swift`、`记录/事项详情页.swift`；按职责拆出手势桥接及工具行，单文件约 200 行软上限。

## 7. 验收与免费额度边界

- 手工矩阵：标题、说明、卡片间隙、左右边距、空列表、列表末端分别横滑；必须均能切模式。卡片横滑不切模式；竖滑与斜滑正常滚动；两个方向与边界均检查。
- 验证卡片随手、回弹、单张展开、按钮命中、删除撤销、展开后纵向滚动、切模式后位置保留；不允许靠多次重试点击通过。
- 详情三个按钮等宽可点击；长中文标题、小屏、大字号、深色、减少动态效果均可用；Markdown、图片和草稿恢复无退化。
- 改造已有双模式 UI 用例覆盖非分段区域的横滑；已有快捷操作用例把长按改成左滑，保留星标/归档/撤销断言。转换与历史测试继续保留。测试坐标由稳定元素边界计算，不写死屏幕像素；操作展开与模式变化提供可查询状态。
- 不新增大量启动 App 的 UI 用例，不增加固定 sleep，不延长时限。局部条件等待失败仍输出首个断言与截图。
- UI 300 秒、verify 30 分钟、package-personal 45 分钟保持。Windows 静态检查不是 Xcode 编译证明；本地完成检查后只跑一次 package-personal 全流程，不要求用户手工依次运行多套流程。
- 声音功能保持移除；不改 Bundle ID、不清用户数据、不引入第三方手势框架、不增加模拟器数量。

## 8. 参考边界

Telegram iOS 的[官方公开仓库](https://github.com/TelegramMessenger/Telegram-iOS)可供研究。本方案的圆形按钮形态以用户提供截图为准，没有声称已逐行审核其当前侧滑组件；不直接搬入 Telegram 的界面框架或源码。
