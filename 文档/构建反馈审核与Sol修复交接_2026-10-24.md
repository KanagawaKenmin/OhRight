## 3. 给 Sol 的最小修复路线

### 第一步：缩短复现路径并补证据

将当前组合用例拆为“历史与搜索范围”和“提醒设置即时保存”两个独立用例。设置用例直接从首页进入设置，不再先录入和浏览资料。预计 UI 从四项变五项，应同步更新数量说明；多一次启动可能增加全量耗时，但单项复现会更快。

诊断运行可使用 `-only-testing:OhRightUITests/ExperienceUITests/<设置用例名>`，复用现有工程、启动和测试参数。最终交付仍执行完整测试，个人打包入口不得继承仅运行一个用例的过滤条件。

在 `应用/L3_外交层/界面/设置/通知与提醒页.swift` 给声音 Toggle 添加稳定标识，例如 `reminderSoundToggle`；可给 Form 添加 `reminderSettingsForm`，便于限定滚动范围。稳定标识解决定位问题，本身不能保证点击有效。

每次失败保存截图、界面树、匹配元素数量、frame、isEnabled、isHittable、点击前后 value、页面错误提示。优先检查本次 xcresult 是否完整并含现成附件；如因中断损坏，再用诊断运行补取。

### 第二步：让测试验证明确结果

先等待唯一目标存在、可用，再在限定次数内滚动设置 Form 直到可点击。当前代码只是“不命中就全屏滑一次”，且先查询 hittable、后等待存在，诊断能力不足。

点击前明确要求 value 为字符串 0 或 1，目标值为其反值；单次点击后用有限时长的条件等待核对精确目标值。示意如下，仍须在当前 Xcode 编译验证：

```swift
let before = try XCTUnwrap(sound.value as? String)
XCTAssertTrue(["0", "1"].contains(before))
let expected = before == "0" ? "1" : "0"
sound.tap()
let changed = XCTNSPredicateExpectation(
    predicate: NSPredicate(format: "value == %@", expected), object: sound)
XCTAssertEqual(XCTWaiter.wait(for: [changed], timeout: 5), .completed)
```

不能只保留 `XCTAssertNotEqual`：如果读取变成 nil，也可能被误判为切换成功。返回并重进设置后重新定位，仍断言等于 expected。

Apple 将 tap 定义为向系统计算的命中点发送事件，将 isHittable 定义为能否在当前位置命中；两者不能代替业务状态断言。参考：[tap](https://developer.apple.com/documentation/xcuiautomation/xcuielement/tap())、[isHittable](https://developer.apple.com/documentation/xcuiautomation/xcuielement/ishittable)、[条件等待](https://developer.apple.com/documentation/xctest/xctnspredicateexpectation)。

若仍未切换，依据界面树和截图判断命中的是整行容器、内部开关还是遮挡区域。只有证实定位层级或命中点有误后，才调整到正确子元素；不要预先硬编码屏幕坐标，也不要不断重复点击直到通过。

### 第三步：按证据决定是否修改产品代码

当前保存链是：Toggle Binding → `AppModel.savePreferences` → `commit` → 仓库保存成功后发布新 workspace。保存入口没有 await；通知重排另有 revision 检查。因此“全部改为异步后多等几秒”没有代码依据。

必要时加仅 Debug 生效的诊断：Binding 是否收到 true、savePreferences 是否成功、提交前后 soundEnabled/revision、有无错误回显。只记状态，不记用户内容。

| 观察结果 | 对应修改方向 |
|---|---|
| Binding 未被调用 | 检查命中目标、控件层级和遮挡，修测试定位或实际交互布局 |
| Binding 收到 true，保存抛错 | 读取真实错误，检查校验或仓库失败，补最小回归后修对应逻辑 |
| 提交成功，模型保持 true，但辅助功能值仍 0 | 检查观察更新、无障碍节点与值暴露，不用直接改模型绕过 UI |
| 提交后模型又变回 false | 查后续写入者及 revision，确认再修并发覆盖 |
| 有限条件等待即可观察到 1 | 定位为观测时机问题，保留条件等待和重新进入验证 |

已通过的 `immediateSettingsPreserveSequentialChangesAndRollbackFailure` 使“所有设置保存都坏了”缺乏依据；它不覆盖真实 SwiftUI 点击和无障碍快照，因此也不能排除 UI 层问题。

当前 `--uitest` 使用内存库。重新打开设置可以验证同一进程中的状态，不能宣称已验证杀进程持久化。若要验证重启保持，另用测试专属磁盘目录或仓库重开测试；不要重启内存测试 App 后期待资料仍在。

## 4. 后续工程优化，按收益安排

1. **先保证错误不会被诊断覆盖。** `构建/验证工程.sh:65` 的崩溃文件复制在 `set -e` 下没有 best-effort 保护，复制异常可能提前退出 trap，跳过摘要和原退出码返回。诊断必须自身限时、容错，并最终保留初始失败码。
2. **摘要保留首个具体错误。** 当前 `indices[-100:]` 在错误多时会丢掉最初断言；应固定保留首个错误、失败用例列表和最后阶段状态。日志写入本次运行目录或本次文件清单，避免本地重复运行读取旧日志。增加机器可读阶段结果，区分 assertion_failure、infrastructure_timeout、build_failure。
3. **预算分层且受总时限约束。** 暂保留 UI 600 秒和单项限时。记录实际阶段耗时，再校准。现在所有阶段上限合计约 40 分钟，verify 外层却为 30 分钟；应明确全局截止和诊断余量，避免最慢路径先被平台硬切。无需为本次失败先重写整个执行器。
4. **让普通 UI 测试环境可控。** 目前 `--uitest` 只隔离存储，仍使用真实 LocalNotificationDelivery。后续可在 Debug 测试装配中注入确定的通知服务，减少无关系统弹窗/通知后台调用；真实权限流程保留单独集成验收。此项是稳定性改进，不是本次根因结论。
5. **简化交付证据。** 每包只给一个明确入口，附包哈希、清单指纹、实际提交、通过项和未通过项。清单由交付过程生成，CI 只校验。后续有条件采用直接提交代码的流程，减少手工混合上传；不要把旧清单一致当作最新版证明。
