# 提醒调度设计

版本 0.2。更新：2026-10-15。本地模式源码已实现，算法测试尚待执行；云端只保留[接口契约](云端接口与交接约定.md)。

## 1. 目标与模式

用户接受启动 App 补排，因此首版采用**本地规则过滤 → 随机洗牌 → 随机时间 → 系统本地通知**。不建设后台续排服务，不依赖服务器，不做学习型推荐。

`ReminderMode = local | cloud` 与首页琐事/计划、时间规则完全独立。当前 local 可用，cloud 为不可用占位；界面不能选择后假装启用了云端。真实切换待未来接入完成后开放。

这里“随机排序”指提醒候选队列和“我现在有空”的抽取顺序；正常浏览时不无故打乱已阅读卡片位置，计划列表仍按截止日期分组。

## 2. 本地规则参数

| 参数 | 默认 | 说明 |
|---|---|---|
| 琐事每日上限 | 1 | 可选 0 / 1 / 2，不强制发满 |
| 时间策略 | 避开免打扰 | 另一选项为全天随机 |
| 每日免打扰 | 23:00–09:00 | 支持跨午夜及多个区间；全天随机时忽略 |
| 同一琐事冷却 | 72 小时 | 按有效计划触发时刻保守计算，不推测已读 |
| 新建/刚补充冷却 | 24 小时 | 避免刚记录就提醒 |
| 随机提醒间隔 | 120 分钟 | 与摘要/期限提醒前后避开 60 分钟 |
| 固定摘要 | 每日 20:30 | 可关闭或改时间，首版一天一个 |
| 期限提醒 | 每计划至多一个，用户可选 | 首版仅提交进入当前窗口的时刻 |
| 排程窗口 | 3 个本地自然日，含今天剩余时间 | 到第三天结束，界面显示具体日期时间 |
| 待触发预算 | 32 条 | 试用工程预算，非 iOS 上限，M0 真机回读验证 |

减少窗口是为简化个人试用，不由签名有效期决定。签名通常 7 天、排程 3 个自然日、每日上限三者不能混为一谈。

## 3. 洗牌与选择

1. 从本地快照筛选 active、允许提醒、未处于暂停提醒时间内的琐事。
2. 按拟定触发时刻排除新建/补充冷却及同事项冷却。
3. 对候选执行标准 Fisher–Yates 洗牌，按洗牌顺序取出；不计算兴趣分或停滞权重。
4. 构造同批未来通知时，将已经选中的事项与时刻纳入冷却，防止一件事重复排入。
5. 保存已提交的选择和时刻；下次启动只补缺口，不把有效请求全部重抽。
6. 测试注入固定随机源；真实运行用本机随机种子生成新批次。

候选为空则跳过。有一条琐事也不强行每天重复。用户主动“换一个”只重新抽当前浏览候选，不擅自重排系统通知。

## 4. 时间抽样

以 Calendar 计算当地自然日的真实边界，避免将夏令时的一天写死为 86,400 秒。

- 当天剔除已过去时段和距当前不足 5 分钟的时刻。
- 避开模式拆开跨午夜、合并重叠免打扰区间；全天随机不加昼夜遮罩。
- 扣除固定提醒和已有随机提醒的间隔范围。
- 按剩余区间长度加权选择区间，再在其中均匀抽一分钟粒度的时刻。
- 可用空间不足就减少通知，有限次数尝试，不循环到“必须抽到”为止。

全天免打扰时显示“当前没有可提醒时间”。完全随机保留每日次数与去重，但允许夜间时刻。修改偏好时只使受影响时刻失效。

## 5. 固定摘要与期限

计划摘要不参与琐事洗牌，按每个触发日期从本地数据生成：逾期 → 今日 → 未来七天 → 其他活动计划，最多列 3 项；同时展示下一步或最近进度。停滞天数可作文字说明，不额外实现复杂评分。

排除 paused、completed、archived、deleted。无活动计划不发。只有远期计划时，也可提示下一小步。标题变动、打开页面、重排不计为实质进度。

每个日期使用一次性通知，不依赖重复通知自动更新内容。默认显示简短摘要，可关闭预览；App 内打开时读取实时数据。修改进度或截止后更新未来摘要。

独立期限提醒保存规则，只有触发时刻进入本地 3 日窗口才提交。未来窗口外显示“尚未排到，打开 App 后按窗口补排”，不声称已交给系统。免打扰冲突应让用户确认更早的允许时间，不能悄悄推过截止。

## 6. 补排时机与窗口耗尽

补排入口只有：启动、回到前台、事项或偏好修改、通知操作、资料恢复，以及 App 获得执行机会时的系统时间变化。

不实现 BGAppRefresh，不发送“请打开续排”的维护通知。用户打开后补齐窗口即可。窗口耗尽时停止新增；不补发过去的随机提醒或错过的摘要。

设置页显示当前模式、下次预计提醒、实际覆盖截止和未排入的明确期限数量。因没有候选而跳过与因容量不足未排入须区分，不能用最后一条通知日期代替计算覆盖范围。

iOS 可处理预先提交的本地通知，但最终横幅受系统权限与专注等设置影响；打开次数不能保证系统一定展示。[Apple 本地通知](https://developer.apple.com/documentation/usernotifications/scheduling-a-notification-locally-from-your-app)。

## 7. 容量与稍后提醒

32 条总预算内，先保留有效的用户主动稍后与明确期限提醒，再安排摘要和随机琐事；空间不足时少排随机，并准确显示缺口。三天最多 6 条随机、3 条摘要，普通个人使用无需大队列管理。

稍后默认 1 小时；避开模式进入免打扰时顺延到下个允许时间。每事项最多一个待触发稍后请求，每日最多 2 次操作，所有稍后 pending 合计最多 4 条；超限提示用户在 App 内调整。

稍后请求按用户确认结果保留，即使顺延后超出普通窗口也不丢弃。完成/删除后不再生成稍后请求。普通每日上限只管主动随机与摘要，不假称涵盖全部用户另设期限和稍后提醒。

## 8. 本地一致性仍须保留

1. 资料显式保存成功后，记录待协调版本，再计算通知；排程失败不能丢失正文。
2. 使用一个串行排程入口，回读 iOS pending 队列，按稳定请求 ID 做增改删。
3. 完成、归档、删除或静音优先取消失效请求，同时清理已知通知中心旧内容。
4. 提交后核对实际接受结果；资料版本变化则使用最新快照再协调。
5. 中途崩溃由下次启动修复，不开发服务端事务、持久化网络重试或消息队列。

ID 建议：`local/idea/{itemID}/{slotID}`、`local/digest/{date}/{zone}`、`local/deadline/{reminderID}`、`local/snooze/{itemID}`。内容版本单独保存；同一语义请求更新沿用 ID。

通知重复回调幂等处理；冷启动先加载资料再跳转。旧通知打开后显示最新状态。前台已经阅读对应事项时抑制重复弹窗。

## 9. 权限、时间与边界

首次启用时申请本地通知权限；拒绝后记录功能仍可用。首版不注册 APNs、不申请云端或特殊通知能力。普通通知声音默认关闭，可在设置打开。

截止时区与时间语义按[数据设计](技术架构与数据设计.md)执行。旅行后若 App 尚未运行，已提交请求仍可能按旧绝对时刻触发；重新打开后重排，不宣称已即时遵循新时区。

免费签名过期后是否还能收到之前通知不作为承诺；先完成续签再使用 App。接口能扩展云端不等于当前签名已有远程推送能力。

## 10. 验收重点

检查本地模式无业务网络依赖，云端不可用时不能切换；固定种子洗牌可复现，无重复选项。验证免打扰、全天随机、冷却、固定摘要、完成即取消、重复启动不洗牌、队列回读、三日耗尽与再启动续排。

真机另验签名与通知权限、关闭 App 后预排通知、覆盖续签保留资料。云同步、后台无人值守和 APNs 不进入本地试用验收。
